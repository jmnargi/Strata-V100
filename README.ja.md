# Strata-V100

**コミュニティが維持する、V100 に焦点を当てた [Strata](https://github.com/Niko1221/Strata) のフォークです。** このフォークは NVIDIA Volta（`sm_70`）のサポートを動作する状態に保ち、Tesla V100 のハードウェアで性能の変更を開発・測定し、V100 以外の機能と修正のために上流の改善を定期的にマージします。

Strata は [Qwen3.8-Flash-Next](https://huggingface.co/Qwen/Qwen3.8-Flash-Next) 向けのオープンソースのローカルランタイムです。GPU、システムメモリ、ストレージを組み合わせて、この大きなモデルを個人のコンピューターで動作させます。このフォークは Strata プロジェクト全体を維持します。対応する他の NVIDIA と AMD のハードウェア、Web インターフェース、OpenAI 互換 API、ツール、画像入力、上流の機能も重要です。

> **Niko（[@Niko1221](https://github.com/Niko1221)）と Strata のオリジナルのコントリビューターに深く感謝します。** このプロジェクトは彼らの作業の上に成り立っています。Strata のモデルランタイム、アーキテクチャ、機能、そしてこのモデルをローカルで動作可能にした作業は、すべて上流プロジェクトに由来します。V100 フォークはその基盤なしには存在しません。実現してくれたこと、そして Strata の開発を続けてくれていることに感謝します。

## このフォークが注力する点

- **Tesla V100 / Volta のサポート（`sm_70`）**：通常の V100 のビルドとランタイムのサポートを維持します。V100 のビルドは CUDA 12.x のツールキットを使用します。CUDA 13 は `sm_70` のコードをコンパイルしません。
- **テストマシン：** Tesla V100-PCIE-16GB を 2 枚搭載しています。GPU 0 は PCIe Gen3 x4、GPU 1 は Gen3 x16 で接続しています。以下のパイプラインの測定では 2 枚のカードを使用します。過去のシングルカードのベンチマークでは x16 のカードのみを使用します。Gen3 x16 のリンクを 2 本備えたシステムは、ここでは測定していません。
- **上流の統合**：これは Strata の独立した代替ではありません。上流の変更を定期的にマージし、V100 の互換性を確認して必要に応じて修正します。上流の新しい機能は `sm_70` を超えるハードウェア要件を持つ場合があります。それらの機能が V100 を自動的に高速化することはありません。
- **Strata コミュニティ全体**：改善、不具合の報告、テスト、ドキュメント、対応する他のプラットフォームへのコントリビューションを歓迎します。

V100 のサポートは、上流のすべての機能や他のすべての GPU 構成が V100 でテスト済みであることを意味しません。ハードウェア固有の機能に依存する前に、該当するコード、リリースノート、測定レポートを確認してください。

### Unsloth Dynamic v3.1 セット（1-4 bit）— 2026年11月8日

[#95](https://github.com/jmnargi/Strata-V100/issues/95) を解決します。セットアップの `--family unsloth` メニューは以前 UD-IQ4_XS（約 4 bit）で止まっていました。現在は Unsloth が 2026-11-04 に公開したリビジョン（コミット `d9620119`）の Dynamic v3.1 のファイルを、約 1 から約 4 bit まで提供します。

| サイズ | ダウンロード | ルーティングされるエキスパート | すべてのエキスパートを RAM に置いた場合の RAM | 注記 |
| --- | ---: | ---: | ---: | --- |
| UD-IQ1_M | 68.0 GB | 32.4 GiB | ~48 GB | 最小。注意深い作業や長い作業では最も弱い |
| UD-Q2_0 | 70.5 GB | 34.8 GiB | ~51 GB | Q2_0 のエキスパート。最速の 2-bit パックと同様 |
| UD-IQ2_XS | 75.8 GB | 39.4 GiB | ~55 GB | Q5_0 ダウンの層が 1 つ |
| UD-Q2_K_XL | 79.6 GB | 42.8 GiB | ~59 GB | Q5_0 ダウンの層が 1 つ |
| UD-IQ3_XXS | 83.6 GB | 46.8 GiB | ~63 GB | Q5_0 なし |
| UD-Q3_K_XL | 89.5 GB | 52.3 GiB | ~68 GB | Q5_0 ダウンの層が 20 |
| UD-IQ4_XS-v31 | 93.7 GB | 56.2 GiB | ~72 GB | Q5_0 ダウンの層が 33。Hub のファイル名が UD-IQ4_XS のため、独自のカタログ名 |

すでに提供していた 5 つのファイル（UD-IQ4_XS、UD-Q4_K_XL、UD-Q5_K_XL、UD-Q6_K_XL、Q8_0）は以前のコミットに固定したままです。新しいコミットでの UD-Q4_K_XL の 2 番目のレイアウト（4 シャード、n-gram テーブルが最後）は、ディスク上にすでにあるファイルから受け付けます。UD-IQ1_S は引き続き拒否します。1 つの層に 2 つのエキスパート形式が混在するためです。

これに必要だったエンジンの作業は、Q5_0 エキスパートのドット積です。重みごとの -16 のオフセットを元の活性化の合計に適用していたため（llama.cpp の CUDA 形式）、ダウン射影が Q5_0 の層は、他のどのダウン形式よりもエキスパートあたり 2-3% 精度が低くなっていました。現在は Q5_1 と Q4_0 の経路および ggml-cpu（CUDA と SYCL）と同様に、量子化された活性化の合計に乗算します。このマシンで合成のエキスパートのパリティ（`native_expert_parity --synthetic`、IQ2_XXS / IQ2_S / IQ2_XS / IQ3_XXS / IQ4_XS のゲートアップと Q5_0 ダウン、浮動小数点の参照に対する相対 L1 誤差）で測定しました。**変更前は 2.40e-2 .. 3.18e-2、変更後は 1.25e-2 .. 1.30e-2** で、同じシードでの IQ4_NL と Q2_0 のダウン（1.29e-2 .. 1.31e-2）と同じです。グループ化されたエキスパートの起動は、ウィンドウ導入前の起動とビット単位で等しいままです（`native_grouped_parity`：すべてのゲート / アップの形式に Q5_0 を追加し、これらのファイルが使う Flash-Next の形状も対象、失敗 0）。エンジンのバージョンは 0.1.45.7 です。セットアップはこれらの 7 つのセットに対して、何かをダウンロードする前に古いエンジンを拒否します。

固定した 5 つのファイル、そのバイト数、その他のすべての形式は変わりません。このカーネルを読むのは Q5_0 の *エキスパート* の重みだけです（デンスの Q5_0 の経路は `native_mmvq` で、変更していません）。そのエキスパート全体の誤差は、浮動小数点の参照に対して 2.4-3.2e-2 から 1.25-1.30e-2 に変わります。

### 上流 v0.2.11 の性能改善の選択的な移植 — 2026年11月5日

この更新は上流の最適化を選択的に移植します。v0.2.11 の完全なマージではありません。より高速なトレリスエキスパートカーネル、より小さなプロンプト用スクラッチバッファ、より少ない PLE ディスクリーダーの割り当て、Linux の CPU/CUDA のゼロスピン修正を追加します。エンジンのバージョンは 0.1.45.6 のままです。

**このフォークのデュアル V100 マシンでの測定：** V100-PCIE-16GB を 2 枚、175 W（GPU0 は Gen3 x4、GPU1 は x16）、Ryzen 5 3600、Gyro-M abliterated Huihui TQ2_0 を使用しました。プロファイルは split 16、パイプラインウィンドウ 2、MTP 4、int8 KV、YaRN 2 付きの 524,288 トークンのコンテキストを使用しました。

| プロンプトのトークン数 | 対照のプロンプト時間 | グループスクラッチ + WMMA オフ |
| ---: | ---: | ---: |
| 2,048 | 2,360.8 ms | 2,214.3 ms |
| 8,192 | 6,932.7 ms | 6,541.0 ms |
| 32,768 | 18,008.6 ms | 17,636.7 ms |

これらはコールドで交互に行う A-B-A-B の実行から得た平均で、サイズと設定の組み合わせごとに 4 回のリクエストです。両方の設定にはすでにトレリス、HC、PLE の移植が含まれていました。これはすべてのコンテキストサイズでの測定された改善でも、リクエスト全体の速度の保証でもありません。

測定した任意の組み合わせは `STRATA_TQ_SUB8=1 STRATA_EXPERT_PAIR=0
STRATA_PF_HC_REGION=1 STRATA_PF_GROUP_SCRATCH=1 STRATA_PF_WMMA=0` です。グループスクラッチは浮動小数点の丸めを変える場合があります。PLE の割り当ての変更にフラグは不要です。ゼロスピンの修正は `STRATA_POOL_SPIN_US=0` で適用されます。日常の設定である 100 での節約は確認していません。

個別の測定、オプションのガード、数値の確認、ビルドの制限、採用しなかった試験的な候補は、[V100 の移植のレポート](docs/NVIDIA_V100.md#selected-upstream-0211-ports-gyro-m-2026-11-05)を参照してください。サービスの既定値は変更しません。

### 上流の選択的な同期 — 2026年10月19日

このブランチは上流のコミット `3d1fb480` から、共有の CUDA エンジンとサーバーの変更を取り込みます。フォークの Volta カーネル、パイプラインの K/V の増加、会話キャッシュの変更は維持します。無関係なデスクトップのパッケージと、Metal、AMD、Intel の各バックエンドの個別の更新は除外します。[同期の範囲](improvements/RELEASE-2026-10-19-V100.md)を参照してください。`sm_70` では CUDA 12.8 を使用します。取り込んだオプションは V100 の性能向上を意味しません。

### 上流 v0.1.39 の統合

この更新は、間にあるリリースを含めて [Strata v0.1.39](https://github.com/Niko1221/Strata/releases/tag/v0.1.39) を統合します。フォークの V100 のテンソルコアのエキスパート、アテンションの変更、非対称の GPU 分割、ディスクの会話キャッシュを維持します。

- **並列リクエスト：** モデル設定で `"parallel": 2` を設定するか、`./setup.sh --parallel 2` を使用します。セットアップは新しい Volta の構成にこの既定値を書き込み、既存の設定は維持します。エンジンは別々の会話を同時にデコードできます。追加のリクエストは空きスロットを待ちます。スロットは追加の GPU メモリを使用し、単一リクエストの速度を下げる場合があります。2 つのスロットのセッションが収まらない場合、エンジンはその旨を通知し、構成を変更せずに 1 つのリクエストずつ処理します。正確性の設定、メモリのコスト、制限は[バッチスロット](docs/BATCHING.md)を参照してください。
- **API とインターフェース：** この更新は OpenAI Responses API、モデル設定、会話キャッシュの監視、スロットごとのメトリクスを追加します。[API の詳細](docs/DETAILS.md#using-it)を参照してください。
- **性能とメモリ：** この更新には、検証パスの起動回数の削減、バイト単位のプロンプトリング、Linux のヒュージページ、RAM 予算の修正、マルチ GPU のオプションが含まれます。明示的な `--layer-split` は、各ステージ自身の層のデンスの重みだけを自動的に読み込みます（上流の `--trim-stage-weights` フラグと `STRATA_STAGE_TRIM` はなくなりました）。解放された VRAM はエキスパートキャッシュに回ります。新しい GPU 向けの最適化は、V100 の速度向上を意味しません。丸めを変える任意の経路は、使用前に測定する必要があります。
- **他のプラットフォーム：** 上流の Intel Arc、古い CPU、追加の AMD の経路は引き続き利用できます。このマシンはそれらのプラットフォームのハードウェア検証を提供しません。

V100 には CUDA 12.x と `sm_70` を含むビルドが必要です。V100 に CUDA 13 のエンジンをインストールしないでください。既存のインストールには明示的な並列設定を推奨します。更新はモデル設定を上書きしません。

### TurboQuant KV キャッシュ — 2026年10月25日

TurboQuant は任意で有効にする KV キャッシュの形式です。各 256 値のヘッドをアダマール変換で回転し、回転した値を Lloyd-Max のコードブックで量子化します。各ヘッドは FP16 のノルムを 1 つ保持します。幅は 1 値あたり 3、4、6、8 bit です。当てはめは最小二乗誤差のみです。この版に QJL の残差はありません。

`--kv tq6`（または `tq3`、`tq4`、`tq8`）を使用します。キャッシュは常駐のみです。VRAM に留まり、ホストのコピーはなく、`--kv-resident` は拒否されます。MTP のドラフト層は INT8 のキャッシュを維持します。セットアップはこれらの値を提供しません。いずれも既定ではなく、日常のサービスは int8 のままです。

設定した 524,288 トークンの容量と、モデルの 12 のアテンション層では、KV キャッシュは次のとおりです。

| `--kv` | セルあたりのバイト数、1 層 | フル容量の KV、12 層 | int8 からの変化 |
| --- | ---: | ---: | ---: |
| int8 | 1,056 | 6.1875 GiB | — |
| tq8 | 1,032 | 6.046875 GiB | −0.14 GiB |
| tq6 | 776 | 4.546875 GiB | −1.64 GiB |
| tq4 | 520 | 3.046875 GiB | −3.14 GiB |
| tq3 | 392 | 2.296875 GiB | −3.89 GiB |

tq6 の主な節約は、フル容量で 1.64 GiB です。これらは計算した容量で、`nvidia-smi` で測定した削減量ではありません。エキスパートキャッシュが解放された VRAM を埋めるため、GPU メモリの合計は約 15,600 MiB のままです。

V100 のプロンプトリーダーは 2 つ目の任意の機能です。sm_70 で `STRATA_PROMPT_ATTN_TQ=1` を設定します。プロンプトの経路のために圧縮されたタイルをデコードします。未設定または `0` の場合は、デコードのアテンションのフォールバックを維持します。KV のバイト数は変わりません。

175 W の Tesla V100 16 GB を 2 枚、IQ3_S、`--spec 4`、`--layer-split 16`、`--pipeline-windows 2`、出力を 2,048 トークンに制限したコールドの条件で、サイズと設定の組み合わせごとに 1 回測定しました。tq6 の設定ではプロンプトリーダーを有効にしました。32,768 プロンプトトークンで、tq6 のプリフィルは 1,687 tokens/s、int8 は 2,117 tokens/s でした。デコードは tq6 が 120.2 tokens/s、int8 が 125.5 tokens/s でした。リーダーを有効にすると、tq6 の 51,746 トークンのリクエストの実時間は 40.3–40.4 s から 31.7–31.9 s に短くなりましたが、int8 の 25.8 s より遅いままです。これらの測定は速度の向上を示しません。ニードルテストでは、122,289 プロンプトトークンまで両方の設定で 15 個中 15 個のセルが見つかりました。これは一般的な品質の結果ではありません。

[詳細レポート](benchmarks/v100-turboquant-2026-10-25.md)と[詳細](docs/DETAILS.md#tesla-v100-fork-benchmark)を参照してください。

### 2 枚の V100 での Gyro-L ペアトレリス — 2026年10月31日

このブランチは agentionai の `Qwen3.8-Flash-Next-Gyro-L-TQ3_0.gguf`（108,323,559,808 バイト、Hugging Face のリビジョン `05892758a67efff0895d23c6df10a6fdb6be8cf4`）を読み込みます。ルーティングされるエキスパートは、アダマール回転した基底で、ペアトレリスの型 TQP5、TQP6、TQP7（ggml の型 147 から 149）として格納されています。パックの手順（`tools/iq_pack.py --compat-bf16`）とカーネルは [docs/GYRO.md](docs/GYRO.md) に記載しています。CPU と CUDA をサポートします。Metal と SYCL にはペアトレリスのカーネルがありません。エンジン 0.1.45.6 以降が必要です。

最初に 2 つのエンジンの不具合を修正する必要がありました。エキスパートのカーネル自体は、作者の ggml に対してすでにビット単位で正確でした。

- **デコードのウィンドウが回転を失っていました。** 折りたたんだパックでは、ウィンドウはエキスパートの入力を回転し、その後エキスパートが読む前に、その回転したコピーを回転していないコピーで上書きしていました。そのためゲート / アップの射影は、デコードしたすべてのトークンで誤った基底で実行されていました。1 回だけの出力はもっともらしく見え、その後ループしました。サーバーは最初のトークンから誤っていました。ウィンドウは現在、層ごとに「イメージを書き込んだ」印を 1 つ保持します。
- **レイヤー分割のプロンプトヘルパー**（任意）は、SwiGLU の出力だけを回転し、グループの行を、ステージの WMMA タイル用のレイアウトのバッファに書き込んでいました。現在は与えられた入力を回転し、自身の H を所有します。

このフォークのペアで測定しました。ハードウェアは Tesla V100-PCIE-16GB を 2 枚（GPU 0 は PCIe Gen3 x4、GPU 1 は x16）、175 W、Ryzen 5 3600 です。設定はレイヤー分割 14、`--spec 4 --spec-min-p 0.70`、KV 増加付きの int8 KV、`--pipeline-windows 2`、262,144 トークンのコンテキスト、サービス自身の環境です。測定は交互に繰り返しました。

| プロンプトのトークン数 | プリフィル（tokens/s） |
| ---: | ---: |
| 2,328 | 632 |
| 8,199 | 1,036-1,084 |
| 16,371 | 1,344-1,411 |

応答は 2K から 32K のコンテキストで 68 から 75 tokens/s でデコードします（520 トークンの応答を繰り返した中央値）。分割点はそれを実行間のばらつき以上には動かしません。読み込みは VRAM にないエキスパートによって制限されます。x16 のカードは 2.3K トークンの読み込みで 15.01 GiB を PCIe 経由でストリームし（レイヤー分割 16 でのプロファイル）、2 つのステージは順に実行されるため、x4 のカードは読み込みごとに約 700 ms アイドルになります。

**このペアで測定したが効果がなかったもの：** `--spec 6` と `--spec 8`、`--spec-min-p 0.50` と `0.85`、固定の `STRATA_PREFILL_CPU_SHARE`、6,144 を超える `STRATA_PREFILL_CPU_SHARE_MAX`、`--prefill-pipe`、`--max-context 131072`、`STRATA_HC_Q8=1`、より大きな `--vram-reserve-mib` です。プロンプトヘルパー自体はここでは遅く（2.3K で 484 対 583 tokens/s）、最初のステージのエキスパートしか使えません。このペアではそのステージが x4 のカードで、読み込みが動かす 16.8 GiB のうち 1.77 GiB をストリームします。`--mtp` と既定の `STRATA_ROUTE_TAIL_SKIP=7` は維持する価値があります。これらがないとデコードは 35.5 と 48 tokens/s に落ちます。

## V100 の性能改善

V100 の作業は、プロンプトの経路、デコードの経路、メモリの使用、ストレージの読み込み、マルチ GPU の実行に及びます。以下の変更はフォークのマージ済みの履歴にあり、各リンクにはそれぞれのテストの方法、ハードウェアの詳細、制限が含まれます。カーネルの時間の改善が、モデル全体のスループットで同じ割合の改善になるとは限りません。

### プロンプト処理

- **Volta での BF16 から FP16 へのテンソルコア GEMM：** Volta にはネイティブの BF16 GEMM のサポートがありません。このフォークは BF16 の重みを正確に FP16 に変換し、スカラーのフォールバックの代わりに V100 のテンソルコアをプロンプトの GEMM に使用します。関連する FP16 のプロンプト活性化イメージは、正しいビット表現を使用します。
- **PLE テーブルの読み込みの高速化：** POSIX の PLE の読み込みを、キューのある `io_uring` の O_DIRECT 操作に切り替え、同期のフォールバックを用意します。測定した新しい 8K の PLE ギャザーは、約 6.9 秒から 7 ミリ秒に短くなりました。
- **Q2_0 MMQ のプリフィル：** Strata の内部のエキスパート型に対して、既存の llama.cpp の Q2_0 の行列と行列の量子化経路を有効にします。測定した 14,486 トークンのプロンプトは、プリフィルのスループットが 6.5% 改善しました（926.1 から 986.2–986.9 tokens/s）。
- **有効な QSA ブロックのみをスコアリング：** 現在のプロンプトの有効な範囲を超えるブロックのスコアリングを避けます。測定した 15,423 トークンのプロンプトで、QSA の選択時間が 91.1% 短くなりました。報告されたテストでは、エンドツーエンドのプリフィルのスループットが 961.0 から 1,111.3–1,112.9 tokens/s に上がりました。
- **Volta のテンソルコアのプロンプトアテンション：** FP32 のフォールバックの代わりに、V100 で `mma.m8n8k4` を使用します。以前の PR は、アテンションカーネルで約 1.6–1.9 倍の速度と、そのテストでのより高いプロンプトのスループットを測定しました。後の上流 PR #600 の移植は、1 つの測定した形状で int8 のアテンションカーネルの時間を 27.9% 削減しました。報告されたエンドツーエンドのプリフィルの差はより小さく（4K–32K のテストで +1.3% から +3.0%）、信頼できるデコードの改善は確認されませんでした。

### デコードとマルチ GPU 実行

- **バッチ化された検証ウィンドウ：** 複数の投機的なデコード位置をまとめて実行し、トークンあたりの起動のオーバーヘッドを減らします。対にした過去のテストは出力の生成が速くなったと報告しましたが、結果はプロンプトと実行時の条件によって変わります。
- **タイル化された QSA ブロックのスコアリング：** 選択したキーのデータをクエリのタイル間で再利用し、繰り返し読み込まないようにします。測定した 256 クエリ / 65K ブロックのカーネルは 3.5 ms から 1.3 ms に短くなりました。スコアごとの演算はビット単位で同一のままでした。
- **Volta の GR の融合と KV 追加のバッチ化：** 検証位置をまたいで処理をまとめ、KV のデータをより少ない起動で追加します。テストしたデュアル V100 の構成では、4K–32K のプロンプトでデコードが 5.6–17.3% 増加し、プリフィルはほぼ変わりませんでした。
- **非対称のデュアル V100 のチューニング：** 2 枚のカードの構成のために、ホストの行の処理、デバイスプランのディスパッチ、メモリの所有権を改善します。以前にインストールした 1 つの構成では、4K–32K でプリフィルが 13.3–18.7% 改善しましたが、デコードの結果は一様でなく、その実行では両方の GPU が熱で速度を落としました。これらの値は各コードの変更を分離したものではありません。
- **重みとディスパッチのオーバーヘッドの削減：** 明示的な分割を使用するときに各カードが所有する層だけを読み込み、不要な CPU の活性化の量子化と空のディスパッチのバリアを避け、任意でペア行のエキスパートカーネルを実行します。GPU0 の測定したネイティブのデンスの割り当ては 1,376.20 MiB から 541.27 MiB に減りました。ペア行のモードは任意です。報告されたモデル全体の結果はデコードの改善を確認しませんでした。

### アテンションカーネルとメモリ転送

- **デコードのアテンション（上流 PR #540 の移植）：** スコアのシャッフルと共有メモリの転送を減らし、累積の順序は維持します。測定したカーネルの時間は、GPU0 で M=1 の場合に 52.90 から 31.13 マイクロ秒、M=8 の場合に 180.42 から 111.85 マイクロ秒に短くなりました。報告されたモデル全体のデコードの変化は小さく、プリフィルは実質的に変わりませんでした。
- **プロンプトのアテンション（上流 PR #600 の移植）：** 4 つの独立した MMA の計算を伴う Volta のテンソルコアの実装を使用します。PR は正確性の確認とカーネルレベル / モデルレベルの測定を報告しています。27.9% のカーネルの削減は、モデル全体の速度が 27.9% 上がることと読むべきではありません。
- **KV ギャザーと GDN の再帰（上流 PR #627 の移植）：** より広い整列した int8 の KV の読み込みを、元の幅の安全なフォールバックとともに使用し、V100 のプロンプトの再帰に複数のアキュムレータを使用します。測定したカーネルの時間は、32K の KV ギャザーで約 10%、4,096 トークンの再帰で約 7% 改善しました。対にしたモデルのプリフィルの差は 0.2% 未満でした。信頼できるエンドツーエンドのデコードの改善は確認されませんでした。

### 会話キャッシュのディスク（任意）

会話の状態には 3 つの階層があります。L1 は有効なセッションと、その常駐するプロンプトのチェックポイントです。L2 は任意のホスト RAM のキャッシュ（`--conversation-cache-mib`）です。L3 は任意のディスクのストアで、再起動をまたいで保存した会話とチェックポイントのグループを保持します。ストリーミングされる KV 層は、エンジンが状態を取得するときに、ホスト側の正となるプールを使用します。

ディスクのストアを使用するには、`--conversation-cache-disk strata-conversations --conversation-cache-disk-gib 25` をエンジンの引数に追加します。パスと正の GiB の予算は、同時に指定する必要があります。ストアは既定では無効で、`--serve` が必要です。`--conversation-cache-mib 0` でも動作します。複数の GPU での `--layer-split` をサポートします。任意で、`--conversation-cache-disk-slots N` はレコード数を制限し、`--conversation-cache-disk-min-free-mib N` はファイルシステムの空き容量を維持します。

エンジンは、保持の処理が有効なチェックポイントを削除する前、またはリクエストがそのブランチを上書きする前に、チェックポイントを保存します。保存した各チェックポイントには、GDN の状態、PLE の履歴、QSA のインデクサーの状態、必要な KV のバッキングが含まれます。このモデルを再開するには、トークンの KV データだけでは不十分です。

関連するチェックポイントは、アーカイブグループごとに 1 つの KV イメージを共有します。エンジンは、チェックポイントごとに接頭辞全体をコピーする代わりに、そのイメージを移動して拡張します。バッキングがまだ有効な場合は、新規または変更された KV ページだけをコピーします。グループは、ディスクのメタデータの上限に達する前に増加を止めます。後のグループは独自のバッキングを持ちます。エンジンは、保存したチェックポイントを、接頭辞の異なる計算の KV バイトと組み合わせません。

アーカイブグループは、保存した会話と同じ L2 のバイト数とスロット数の上限を使用します。ディスクの階層が有効な場合、L2 の容量のために追い出されたものは L3 に移動します。L2 への受け入れに成功しても、イメージをディスクにも書き込むことはありません。イメージが L2 に収まらない場合、エンジンは L3 への保存を試みます。物理 RAM とディスクの空き容量の上限は引き続き適用されます。最小トークンの設定は、チェックポイントのアーカイブにも適用されます。

チェックポイントの保存は最適化であり、必須ではありません。ホスト RAM の下限またはディスクの予算がイメージを拒否した場合、エンジンはチェックポイントを破棄し、破棄をログに記録して、サービスの提供を続けます。サーバーは停止しません。セッションは正しいままで、そのチェックポイントの再利用だけが失われます。

検索は、有効なセッション、L2、L3、アイドル状態のバッチスロットを通じて、互換性のある最長の接頭辞を選択します。トークン、イメージの識別子、制御ベクトルのモードが一致する必要があります。以前のメッセージの編集では、再利用は最初に変更されたトークンの前の保存済みチェックポイントで終わります。エンジンは接尾辞を再度処理する必要があります。その位置の再帰の状態なしに、一致する任意のトークンから再開することはできません。`--prompt-cache` を増やすことは、チェックポイントの保存の代わりにはなりません。

L2 のアーカイブは、復元の後も利用できます。有効な L3 のイメージは、バイト数と物理 RAM の下限が許す場合に L2 に昇格します。そのチェックポイントの限られた一部だけが、有効なセッションに常駐します。1 つのブランチの復元は、保存したアーカイブから他のチェックポイントを削除しません。

ディスクストアは、追記のみの会話のチェーンをサポートします。継続するチェーンは、新しいトークン ID、チェックポイント、実行の状態、KV ページを追加できます。L2 からの追い出しは完全なシードのイメージを書き込み、GPU のキャプチャを必要としません。巻き戻しは、元のチェーンを置き換える代わりに、別のブランチを開始します。チェックポイントのアーカイブでは、ファイルの形式は変わりません。

ディスクのパネルにはチェックサムとバージョンのフィールドがあります。シードは一時ファイルと名前の変更を使用します。不完全な追記は、最後の完全なパネルまで復旧します。無効または互換性のないレコードは削除されます。ディスクストアは、バイト数の予算、レコード数の上限、空き容量の下限を守るために、最も長く使われていないチェーンを追い出します。したがって、L2 も L3 も無制限の履歴を提供しません。両方の階層が必須のチェックポイントを追い出している場合、リクエストは不足している接頭辞を再度処理する必要があります。

エンジンは、ルートの保持が有効な場合、共有のシステムプロンプトのルートを L2 に 1 回キャプチャします。L3 は、L2 からの追い出しまたは L2 への受け入れの失敗のときにルートを受け取ります。L2 が無効な場合、有効な L3 はルートを直接受け取れます。`--conversation-cache-keep-root` と `--conversation-cache-disk-keep-root` は、各階層でのルートの保持を制御します。それぞれの `--no-` の変種は、その保持を無効にします。ルートは通常のイメージより追い出されにくく、リクエストによるチェックポイントの明示的な固定は保護されたままです。

ディスクの階層は並列の実行を追加しません。同時リクエストのメモリのコストは[バッチスロット](docs/BATCHING.md)を参照してください。キャプチャは、リクエストが必須のセッションのバイトを上書きする前に完了する必要があります。復元は同期的です。L2 からの追い出しの書き込みはホストのスナップショットを使用し、ディスクの I/O のレイテンシを追加する場合があります。必要とする会話とチェックポイントの履歴に合わせて、両方のキャッシュの予算を設定してください。チェックポイントの保持の検証は [V100 のガイド](docs/NVIDIA_V100.md)を、以前の測定は[ディスクのベンチマークのレポート](benchmarks/v100-l3-conversation-cache-2026-10-03.md)を参照してください。

#### V100 での測定結果

このフォークの 2 枚の V100 のレイヤー分割の構成で、33,725 トークンの会話を 25 GiB の NVMe キャッシュから再開するのに、読み込みに 1,614.6 ms、復元に 315.8 ms かかりました。22 の新しいトークンを含む、再開したプロンプトのフェーズ全体は 3,015.1 ms かかりました。同じ 33,725 トークンの接頭辞のコールドの読み込みは 20,332.7 ms かかりました。これは再開したリクエストで **6.74x の高速化** と **プロンプトのレイテンシの 85.2% の削減** です。943.6 MiB のレコードは、両方の GPU でバイト単位で正確なメインモデルの状態と同一の出力を復元しました。再起動からの復旧はバイト単位で正確な一致に合格し、壊れたレコードのフォールバックは一致する出力を生成しました。[ベンチマークのレポート](benchmarks/v100-l3-conversation-cache-2026-10-03.md)を参照してください。

このフォークの 2 枚の V100 のレイヤー分割の構成（Qwen3.8-Flash-Next Q2_0、int8 KV）で測定しました。2 つの会話をスクラッチキャッシュを通して交互に処理し、8 回のリクエストで `corruptions=0 evictions=0` で正しく提供しました。会話ごとの 1 つのチェーンファイルは、それぞれ +12 の新しいトークンの 3 回のパークで 238 MiB -> 594 MiB に増加しました（完全なスナップショットのストアでは、100k+ トークンでパークごとに新しい ~2.4 GiB のファイルを書き込んでいたはずです）。新しい短いチャットの最初のパークはチェーンをシードします（~118 MiB：層ごとに 1 つの K/V ページと、モデルの固定の実行状態）。その後、どのパークも差分（+12 トークンで ~118 MiB）で、読み戻し / 復元の経路は変わりません（読み込みに ~0.4 s、復元に ~0.04-0.08 s）。

### レイジービジョン（任意）

画像エンコーダー（`strata-vision`）は、動作している間、約 1.74 GiB の VRAM（1 枚目の GPU に 1.43 GiB、2 枚目に 0.31 GiB）を保持します。レイジービジョンでは、画像のリクエストの間は動作しません。その VRAM はエキスパートキャッシュに残るため、テキストのみの処理は常駐するエキスパートの数を維持します。

有効にするには、モデル設定に次を追加します。

- `"vram_elastic": true`（エンジンのフラグは `--vram-elastic`）：エキスパートキャッシュが分割されるため、エンジンはリクエストの間に VRAM を返して再度取得できます。
- `"vision": {"lazy": true, "idle_s": 900}`：エンコーダーは最初の画像のリクエストで起動し、画像のリクエストがないまま `idle_s` 秒たつと停止します（900 = 15 分）。エンコーダーにはエンジンの 1 リクエストずつのモードが必要なため、`"parallel"` と組み合わせないでください（または、`POST /v1/vram` など別の方法でエンコーダーに VRAM を渡してください）。

動作は次のとおりです。

- テキストのリクエストはエンコーダーを起動しません。画像のリクエストは、まずエンジンに GPU の VRAM を返すよう指示し（GPU ごとに 1 つの予約で、レイヤー分割では `[1700, 600]`、1 枚の GPU では `[1800]`、`"vram_mib"` で上書きできます）、その後でエンコーダーを起動し、エンジンがアイドルの間に画像をエンコードします。
- 画像のリクエストがないまま `idle_s` 秒たつと、エンコーダーは停止し、エキスパートキャッシュは元のサイズまで増えます。エンコードした画像はディスクにキャッシュされるため、同じ画像を再度送ってもエンコードし直しません。
- このフォークの 2 枚の V100 のレイヤー分割で測定しました。エンコーダーがアイドルの間、キャッシュは **14,005** の常駐エキスパートを保持し（エンコーダーが常駐する場合は 12,688）、コールドの画像のリクエストは **5.9 s** で応答し、エンコーダーの解放後は両方のキャッシュが 14,005 に戻りました。[詳細](docs/DETAILS.md)を参照してください。

## コントリビューション

コントリビューションを歓迎します。手伝うのに V100 は必要ありません。ドキュメント、テスト、セットアップ、サーバーの動作、API の互換性、対応する他のデバイスの改善は役に立ちます。V100 固有のコードと性能の結果は、実際の Volta のハードウェアでの検証から恩恵を受けます。

1. 作業の重複を避けるために、[未解決の Issue](https://github.com/jmnargi/Strata-V100/issues)と [pull request](https://github.com/jmnargi/Strata-V100/pulls)を確認します。
2. 広範な上流の機能については、変更が [Niko の上流のリポジトリ](https://github.com/Niko1221/Strata)に属するかを確認します。このフォークは上流の変更を定期的に統合します。焦点を絞った V100 の修正と測定は、ここで提案できます。
3. 焦点を絞った変更を行い、テストに使用したハードウェアと正確な手順を説明し、関連するテストを含めます。
4. 性能の主張には、ベースラインと候補、実行時の設定の全体、ワークロード、繰り返しの回数、制限を報告します。可能な場合は生データまたは再現可能なコマンドを含めます。カーネルの時間とモデル全体のスループットを分け、測定が示さない改善を主張しないでください。
5. このリポジトリの `main` ブランチに対して pull request を作成します。変更が V100 固有か、上流の統合か、Strata の一般的な改善かを説明します。認証情報、個人の構成、無関係なローカルのファイルを変更に含めないでください。

現在の測定の方法は [`benchmarks/README.md`](benchmarks/README.md) と [`docs/DETAILS.md`](docs/DETAILS.md) を参照してください。コントリビューションには、プロジェクトのライセンスと、含まれる構成要素とモデルのファイルのライセンスが引き続き適用されます。
